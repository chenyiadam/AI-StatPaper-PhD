# stat-simulation-audit · 实验设计与代码审计

## 硬性纪律

1. **确定性代码做重活，AI 只做判断**（Polaris 原则）：实验永远由脚本运行，
   AI 不"心算"任何数值结果；AI 解读只能引用表格中真实存在的数字。
2. **跑之前先审计**：审代码远比审论文便宜；正式开跑前必须过本 skill 审计。
3. **失败要记录**：方法不收敛/发散记录为失败率进表，禁止静默丢场景。
4. **种子即身份证**：每个数字可由（场景 × 重复 × 种子规则）复现。

## 工作流

### A. 模拟设计（写代码前）
1. `prompts/04-实验设计与审计.md` **P13** 生成五件套：场景网格表（每个取值
   对应定理哪条假设的满足/边界/违反）→ DGP 伪代码（逐式对应论文公式）→
   指标定义表（公式 + 对应定理结论）→ 基准公平性协议（基准也要调参）→
   失败协议。
2. 用骨架起步：`templates/simulation/sim_design.R` 或 `sim_design.py`
   （已内置种子规则化、指标一次算全、tidy 输出）。
3. 对照 `checklists/C3-实验检查清单.md` A、B 组检查。

### B. 代码审计（开跑前）
用 **P14** 逐项审计：DGP 与文档一致性（第一大错误源）→ 种子纪律与
隐藏随机源 → 统计正确性（覆盖率对真参数、TPR/FDR 分母、size 公式、
CV 不泄露）→ 边界与失败捕获 → 可复现性 → 性能陷阱。
审计后执行 **10 分钟冒烟测试**：n=50, p=10, rep=20 验证输出形态与数量级。

### C. 结果解读（跑完后）
1. `prompts/04` **P15**：表到文字的忠实转换——只用表里数字、每个模式带
   具体数字、与理论预期对表、**不一致的结果如实写出**并给候选解释。
2. AI 必须输出"数字-单元格对照表"，作者逐个核对（数字溯源纪律）。
3. 呈现规范：three-digits rule、最优值加粗并注明判据、caption 自含
   （用 `prompts/05` P19）。

### D. 真实数据分析
1. `prompts/04` **P16**：数据适配性判断 → 预处理协议（缺失值两种处理对照、
   离群值规则先于看数据）→ 主分析 + 敏感性分析 → 解读边界声明
   （"与…相一致 / 表明 / 证明"的措辞等级）。
2. 对照 `checklists/C3-实验检查清单.md` D 组；数据可得性声明必写。

### E. 复现包（投稿前）
1. 目录按 TIER 4.0：`data/ code/ output/ docs/` + README（一键运行命令）。
2. 环境锁定：`requirements.txt` / `renv.lock` / `environment.yml`，含解释器版本。
3. 全部图表由脚本重生成且数字与论文一致；代码存 Zenodo/OSF 取 DOI。
4. 敏感信息扫描：API key、本地路径、个人身份信息清零。

## 与其他部件的联动

- 理论一致性：λ 的阶、稀疏度 s、误差假设在"定理-模拟-附录"三处一致
  （与 stat-theory-check 联动，C2-D 组）。
- 数字对账（Polaris 规则）：论文正文百分数/小数必须与实验输出匹配
  （±0.01 容差；小整数、年份、表号豁免）——投稿前由作者按
  "数字-单元格对照表"全量核对。
- 表格格式：`scripts/fig_table_check.py`（图表被引用、caption 自含）。

## 输出格式

审计报告：`编号 | 位置(文件:行) | 问题 | 为什么是问题 | 修法 | 严重度`，
末尾附冒烟测试步骤清单与"可开跑判定"（AI 初判，作者确认）。
